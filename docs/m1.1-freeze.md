## 1. Role-table decisions (final for M1.1)

The table is authoritative, and names alone never create a leader.

| `norman/guildmaster` | **MILITIA** (explicit) | 9.0.2 inspection shows no military command function: no `patrol` goal, no armour or ranged tool classes, and its only special goal is `inspect_construction`. It is listed explicitly so it stops appearing as "ambiguous". |
| SOLDIER types | unchanged | See `docs/m1.1-report.md` §3 |

Example impact: a village with a seneschal now counts one LEADER. That alone doesn't change GARRISON, which needs ≥3 SOLDIER/LEADER plus infrastructure. The fresh harness village stays GUARD_POST.

## 2. The player-owned invasion path, traced in code and checked on the server

| # | Step | Code | Server evidence (scenario I, 3 owned militia) |
|---|---|---|---|
| 1 | An owned unit is inside the village: **presence is not aggression** | `ThreatTracker.classify`: HYW_ENEMY only if `HywCombatFactionService.isEnemyOfIdentity`. That uses HYW's rule: exactly one null owner, or an explicit HOSTILE relation. An owned unit against a NEUTRAL village faction gets no reason. | I1: 3 owned units idle in the village through 25 s of scans. 0 threats, no "Threat detected". |
| 2 | The unit attacks a resident | `CoreEvents.onDamage` → `IncidentLedger.record` puts `lastAttackOnVillage[attacker][village]` when the victim is a (non-raider) resident. `classify` adds RECENT_ATTACKER, and ATTACKING_RESIDENT if the unit's HYW target is a resident (indiscriminate mode). | I2: each attacker listed **once**, with `RECENT_ATTACKER` (one also with `ATTACKING_RESIDENT`) |

| 4 | The defender engages | `BridgeEngageTask`: Millénaire's own `performAttack`, weapon and cooldowns. It leaves the fight when Millénaire clears the target or the unit stops being a threat. | I3: 24 hits, all by defenders (11 distinct) |

| 8 | Same-tick escalation (no damage event) | `reconcile` | D5-b: HOSTILE right after 3 same-tick hits, NEUTRAL with a WARN "(found by reconciliation)" 2 s later |

## 4. Static state and integrated-server review

Every `static` mutable field in the mod:

| Field | Lifetime | Verdict |
|---|---|---|
| `HywMillRuntime.current` | Set at `ServerAboutToStartEvent` (HIGHEST), cleared at `ServerStoppedEvent` (LOWEST). If a start arrives without a stop, it warns and replaces. | Per world ✅ |
| `RoleTables.current` | Replaced wholesale by every datapack (re)load. A single-player world load runs its own datapack load, before the server starts. | Per world ✅ |
| `MillenaireGoalBridge.INSTALLED` | Cleared and re-filled at every `ServerStartedEvent(LOW)`. `replace` unwraps an existing decorator, so a second world never double-wraps. Millénaire's registry is JVM-global and is reset by Millénaire itself on each start. | Per world ✅ |
| `Services.*`, `Integrations.STATE` | Mod lifetime (which integrations are present, plus diagnostics). A `LinkageError` disables an integration for the rest of the JVM, which is correct because the classes won't change. | Intended ✅ |
| `HmLog.LAST` (log throttling) | JVM lifetime, pruned past 4096 keys (entries older than 10 min) | Bounded ✅ |

Other single-player specifics:

- `EntityJoinLevelEvent` and `LivingDamageEvent` handlers return on the client side.
- Ticks, commands and SavedData run on the integrated server thread.
- `GarrisonLedger` and `IdentityClearance` are per-world SavedData.
- Counters and the faction registry live in the runtime, so they start fresh per world.

No problem found.

## 5. Remaining known limitations (unchanged by design, or out of M1.1 scope)

1. **D6 is UNVERIFIED.** The code path (ATTACKING_ALLY_PLAYER with a reputation/first-strike policy) is covered only by the same classifier as the verified paths. It has no end-to-end test with a real player.
2. **The single-player lifecycle** is verified by review and by repeated dedicated-server start/stop cycles, not by a real client session.
3. **Proactive engagement is still M1 behavior**, by agreement. The `hunt_monster` bridge lets idle defenders engage any tracked threat, including unowned HYW units flagged only by HYW's null-owner rule (for example bandits). It never applies to owned or neutral units. `proactive=false` lands with M2.
4. HYW **team** relations (`getPlayerRelationWithTeam`) are not reconciled; direct identity relations are.
5. Our identity markers are cleared or managed only through residency. A former resident of a deleted village keeps its marker.
6. Villager roles affect only the tier, the profile and reporting. No behavior reads LEADER/SOLDIER yet.

## 6. What M2 should build on

These are the stable M1.1 foundation classes (paths under `src/main/java/dev/hywmill/`). M2 should extend them rather than replace them.

| Area | Classes | Contract for M2 |
|---|---|---|
| Runtime | `core/HywMillRuntime`, `core/VillageScheduler`, `core/CoreEvents` | Per-server state goes into the runtime; periodic per-village work uses `VillageScheduler.isDue`. |
| Services and isolation | `core/Services`, `core/Integration(s)`, `faction/CombatFactionService`, `settlement/SettlementSource` | New Millénaire/HYW calls go only through these interfaces, implemented in `integration/millenaire` and `integration/hyw`. |
| Identity (persistent contracts) | `faction/FactionIds` (frozen namespace), `faction/FactionRegistry`, `faction/FactionMarker`, `faction/IdentityClearance` | Never change `FactionIds` or `hywmill_garrison_ledger`. `villageId`, `factionId` and the future `controllerPlayerId` stay separate. |
| Classification | `classify/*` (`RoleClassifier`, `RoleTable`, `RoleTableLoader`, `RoleTables`, `BuildingRole`, `VillagerRole`), `data/hywmill/hywmill_roles/*.json` | The doctrine profile reads roles from here; the table stays authoritative. |
| Profile inputs | `settlement/SettlementSnapshot`, `settlement/VillageRecord` (ledger format 2), `settlement/GarrisonLedger`, `settlement/GarrisonUpdater`, `fortification/FortificationScore`, `military/MilitaryTier` | Capacity (from the operational variant and level only) and the controller id are added here as a ledger format bump with migration. |
| Threat and alert inputs | `military/ThreatTracker` (reasons), `military/IncidentLedger` | M2's ALERT/ENGAGED/RECOVERY and `proactive` rules consume the existing reasons. `proactive=false` = do not start on HYW_ENEMY-only. |
| Diplomacy | `military/EscalationGuard`, `military/DiplomacyPolicy` | Keep ALWAYS_REVERT until the war system exists. |
| Behavior seams | `integration/millenaire/BridgeDecorator` and its subclasses, `BridgeEngageTask`, `BridgeHideTask`, `MillenaireGoalBridge` | The approved M2 reserve decorates `defend_village` the same way. Bridge-only branches must keep the `LinkageError` guard. |
| Tests | `devtools/server-harness/harness.py` (A–I, M, `optional`), `src/test/java/**` | M2 changes TEST C's expectation (proactive=false) and adds its own scenarios. |
