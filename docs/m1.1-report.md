## 2. What changed

### 2.1 Step 2: runtime context (non-behavioral)

- **`core/HywMillRuntime`** holds all per-server state: threat tracker, incident ledger, faction registry, counters and the village-list cache.
  - It is created at `ServerAboutToStartEvent` (HIGHEST) and dropped at `ServerStoppedEvent` (LOWEST).
  - Decorators and tasks read it null-safely. Commands use `require()`.
- **`faction/FactionIds`** is now a pure derivation, with the frozen namespace documented as a persistent contract. The "which UUIDs are ours" set moved to the per-server **`FactionRegistry`**.
- **`core/VillageScheduler`** gives each village a stable phase, so each village is still updated every interval, but not all in the same tick.
  - The village list is re-read once per ledger interval.
  - The threat scan is the same per village (every `threatScanInterval`), with the load spread across ticks.
- **`BridgeDecorator`** makes the bridge-only `canStart`/`start` branches catch `LinkageError`, because Millénaire's `GoalScheduler` only catches `Exception`. On such an error it disables the HYW integration and returns an already-finished task (`FinishedTask`).
- **Logging:** INFO is used only for tier, garrison or fortification changes. Other record diffs go to the diagnostic channel.
- The only observable difference is scheduling. The approved plan included the stagger, and A–F were unchanged (24/24).

### 2.2 Step 3: neutral uncrewed siege weapons

`HywCombatFactionService.isCombatUnit` / `findCombatUnits` now also require `!isNeutralUncrewedSiegeWeapon()`. HYW defines this as a `CrewOperatedSiegeWeapon` with no operational crew, no owner and no passengers (bytecode-verified). The weapon becomes a combat unit again as soon as it is crewed, owned or ridden.

### 2.3 Step 4: escalation reconciliation

- `EscalationGuard.reconcile` runs every 200 ticks, staggered per village. For every registered village faction it asks HYW for permanent HOSTILE relations in both directions:
  - outbound: `RelationSystem.getAllRelations(faction)`;
  - inbound: `getRelation(holder, faction)` for every holder in `getAllRelationData()`, which catches manual one-way relations.
- Every hit goes through the same path as the damage-event fast path: counter, WARN and reset to NEUTRAL (when `preventPermanentEscalation=true`).
- The keep-or-revert decision is behind **`military/DiplomacyPolicy`**. It is `ALWAYS_REVERT` now; future declared wars can plug in here.
- **Unchanged, as you required:**
  - HYW's temporary retaliation (`TemporaryHostileTargetManager`).
  - HYW's null-owner "enemy" rule, which is why unowned bandits are hostile. It isn't stored in `RelationSystem`, so reconciliation can't touch it, and there is no allow-list.
- `dev playerhit <targets> <amount> <repeat>` can now hit several times in one tick. Hits 2 and 3 land inside invulnerability frames, where HYW counts them but NeoForge fires no damage event.

### 2.4 Step 5: classification, fortification, tier, ledger format 2

- **Role tables (datapack):** `data/<ns>/hywmill_roles/*.json`, loaded by `classify/RoleTableLoader` on every datapack (re)load. Files merge in resource-location order, and invalid entries are skipped with a WARN.
  - Shipped: one file per culture (`byzantines`, `indian`, `inuits`, `japanese`, `mayan`, `norman`, `seljuk`).
  - A JUnit test checks every shipped id against the Millénaire 9.0.2 data.
- **Villager rules** (`RoleClassifier.villager`):
  1. Millénaire's `hostile` tag → OUTLAW. This is checked separately and before the table.
  2. Explicit table entry (authoritative).
  3. Child → CIVILIAN.
  4. `helpInAttacks` → MILITIA.
  5. Otherwise CIVILIAN.
- **Building rules** (`RoleClassifier.building`):
  1. Explicit table entry. `NONE` excludes a building.
  2. Millénaire `isBorderPost()` → BORDER_MARKER.
  3. Role derived from Millénaire's `WallType` data:
     - wall types with `wallSpawn=false` (every culture's `borderposts`): every piece is BORDER_MARKER;
     - otherwise the tower piece is TOWER, the gateway piece is GATE, and wall, corner, cap and slope pieces are WALL.
  4. No role.
  - The `patrol` tag and plan-name keywords are no longer used anywhere in classification. Tags are only reported.
- **Ambiguous types are reported, not promoted.** An unlisted `helpInAttacks` type with a `chief`, `archer`, `defensive` or `defender` tag is still MILITIA by fallback. It is listed in `village info` and in the log when the record is first created. On the test village this flags `millenaire:norman/seneschal`.
- **Fortification and tier:** exactly the §1.5 values you approved (README has the table). ARMOURY and TRAINING give 0 points but count toward GARRISON. BORDER_MARKER gives 0 points and is reported.
- **Ledger format 2:**
  - `VillageRecord` stores `villagerRoles`, `buildingRoles`, `ambiguousTypes` and `wallSegmentsPending`. It drops M1's `wallSegments`, `wallTowers`, `defensiveBuildings` and `militaryPlans`.
  - Format-1 records keep their identity and history (village id, faction id, first seen, update count). They are flagged `needsRecompute` and recomputed at their next scheduled update, **even if the village is inactive**.
  - The load logs the migration at INFO, and so does each recompute.
- **Unit tests** now see Minecraft classes (NBT, Gson) through `testCompileClasspath`/`testRuntimeClasspath extendsFrom`. No game bootstrap is needed. Millénaire and HYW stay off the test classpath.

### 2.5 Step 6: identity marker lifecycle

- With `bridge.markVillagers=false`, `FactionMarker.ensure` now **removes** a marker carrying one of our village-faction UUIDs, on join and on every sweep. Markers carrying any other identity are never touched.
- **`/hywmill admin clear-identities [all]`** (op 3) clears loaded residents of the nearest village, or of all villages. It records them in a persisted clearance (`data/hywmill_identity_clearance.dat`).
  - Unloaded residents are cleared when they load.
  - Nothing re-marks them until **`restore-identities [all]`**.
- `status` shows the clearance state and the removed-marker counter.
- README has an uninstall procedure: clear, load each village once, save, then remove the JAR. A fully automatic uninstall is impossible, because nothing runs once the mod is gone.

## 3. The SOLDIER/LEADER question (tier needs villager roles)

The approved tier needs SOLDIER/LEADER counts, but the §4 plan scheduled the villager role table for M2. The Millénaire data settles this: **almost every adult male type is `helpInAttacks`**. In Normandy that includes farmers, carpenters, glassblowers, shepherds, smiths and the alchemist's apprentice. No Millénaire flag separates a guard from a farmer. So no rule without a table could give the approved tier its meaning.

**Choice:** M1.1 ships the villager role table as well, but uses it **only** for the tier and for reporting. No combat or goal code reads villager roles yet; that is M2. The table is deliberately conservative:

| Role | Types |
|---|---|
| SOLDIER | norman `guard`, `orderguard`; byzantines `guard_byzantine`, `soldier_byzantine`, `playersoldier_byzantine`; indian `soldier`; japanese `samurai`; mayan `warrior`; seljuk `turk_soldier`, `turk_lonesoldier` |
| LEADER | norman `knight`; byzantines `centurio_byzantine`; indian `rajputgeneral`; japanese `samuraigeneral` |

Everything else falls through the documented rules. Civil chiefs (seneschal, guildmaster, raja, vali, kuge, Mayan kings…) are MILITIA by fallback and **reported as ambiguous**, so you can decide them explicitly (§6).

**Building table curation notes** (all ids verified against the 9.0.2 data):

- Fort towns count as FORT_TOWNHALL: `norman/fort`, `largefort`, the player forts, byzantine `fortress`/`kastron`/`playerfortress`, indian `fort`, `japanesefort`, and seljuk `sarayfort`/`sarayfortplayer`.
- Sub-buildings that house soldiers count as BARRACKS when they are a dedicated barracks: `largefort_a_barrack`, `fortress_a_barracks` and indian `fort_a_soldierhouse(2)`.
- Seljuk `sarayfort_a_soldier*` rooms and `barracks_a_bed*` sub-rooms are **not** listed. The parent (fort or barracks) already counts, and four 4-point rooms would inflate a single fort.
- Norman `fort_a_left/righttower` (they house guards) are WATCHTOWER.
- Outlaw and quest buildings (bandit towers and forts, Mayan quest camps) and lone keeper towers are not listed.

## 5. Harness bugs found and fixed (test-side only)

- **E1 (resurrection) never fired in a fresh world.** Millénaire's `VillageIntegrityChecker` has two conditions, and the harness broke both:
  - It counts a dusk only at `dayTime % 24000 ≥ 13000`. The harness set 12900.
  - It requires `gameTime − lastRespawnTick ≥ 6000`, where `lastRespawnTick` is the spawn tick. The world was only about 6000 ticks old.
  - Fix: E now `tick sprint`s the game clock to 9000 first, and sets dusk + 500. M1's manual test had passed because that world was older.
- **F1 (vanilla zombie) was flaky.** At `dayTime 18000` every villager is in the `rest` goal and ignores a zombie beside them. F1 now runs at noon with a helmeted zombie, picks a defender that isn't resting, and retries with up to 3 defenders.
- **D5-b** first run: the WARN regex expected `" found by reconciliation"`, but the log reads `"(found by reconciliation)"`. The relation had in fact been reset to NEUTRAL 2 s after the hits, with the WARN logged. The first final run (35/36) is kept in the evidence folder next to the fixed rerun.

## 6. Open items and limitations

- **Please review the ambiguous types.** Chiefs such as `norman/seneschal`, `norman/guildmaster`, `seljuk/turk_vali`, `japanese/kuge` and `indian/raja` are MILITIA by fallback. If any should be LEADER (for example `turk_vali`, who is an archer chief of the Seljuk fort), it's a one-line table entry.
- **D6 and single-player** are still untested (§7).
- **Out of scope for M1.1:**
  - HYW **team** relations (`getPlayerRelationWithTeam`) are not reconciled; only direct identity relations are.
  - Markers on entities that are no longer residents of any village (for example, a villager whose village was deleted) are not swept. `markVillagers=false` and clear-identities act through residency.
- **`proactive` is still M1 behavior**, as agreed. The `hunt_monster` bridge still engages any tracked threat. The change to `proactive=false` lands with M2 doctrine, and TEST C wording changes then.

## 7. D6 and single-player checklist (your client, about 15 minutes)

1. Install NeoForge 21.1.226 with the three JARs. In `config/hywmill-common.toml` set `devCommands = true` and `verboseLogging = true`.
2. **Single-player:** create a world, spawn a village on plains (`/millenaire spawn at ~ ~ ~ "norman/militaire" 100`) and stand in it.
3. `/hywmill village info`: check the new `Villager roles:` and `Building roles:` lines. A `militaire` village should show FORT_TOWNHALL and `guard` residents as SOLDIER.
4. `/summon hundred_years_war:militia ~5 ~ ~ {OwnerUUID:[I;1,2,3,4]}`, then hit it until it retaliates and chases you, staying near guards.
5. **PASS D6:**
   - `/hywmill threats` lists it with `ATTACKING_ALLY_PLAYER`;
   - `/hywmill incidents` shows a `millenaire:villager` → militia hit;
   - `/hywmill dev relation 00000001-0000-0002-0000-000300000004` shows NEUTRAL.
6. Hit a villager 3–4 times quickly, then wait 10 s. `/hywmill status` should show `escalation guard: detected≥1 reverted≥1`, and the relation to you should be NEUTRAL.
7. `/hywmill admin clear-identities`, then `/hywmill dev inspect @e[type=millenaire:villager,limit=1,sort=nearest]`: the result should be `marker=null`. Then run `/hywmill admin restore-identities`.
8. Save and quit to title. Open a **second** world, then reopen the first:
   - `/hywmill status` shows all three goals bridged and fresh counters (a new runtime per world);
   - step 5 works again (integrated-server lifecycle).

Please send back PASS/FAIL per step, plus `logs/latest.log` if anything fails.
